## 사용자 요구사항과 단계

- 초등학교 교사가 운영하는 한국어 브라우저 서비스. PC/크롬북 URL 입장, 학생 회원가입 없음. 교사가 방을 만들고 학생은 방 코드와 교사가 허용한 닉네임 또는 번호로 입장. 방 최대 30명. 교사 포함 여부는 구현 시 명시할 설정으로 관리.
- 가벼운 2D 쿼터뷰/위에서 내려다보는 RPG. 파스텔톤 우주 배경, 둥근 버튼. 디자인과 기능 분리, 캐릭터/아이템 이미지는 사용자가 나중에 제공.
- 첫 입장은 전원 같은 이름 없는 LV1 작은 소행성, 아바타 선택 없음. 학생 식별 닉네임은 별도 표시. 초기 선택을 제시한 중단된 이전 요청보다 최신 요청 우선.
- 향후 LV2부터 별자리 캐릭터 16종 선택, LV3~LV5 진화 구조. 사용자 원문 'LV3, LV4, LV4'는 오타 가능성이 있으므로 최종 명칭은 미확정. 1→2/2→3/3→4/4→5 요구 경험치 15/20/25/30으로 해석하되 확인 가능한 설정 데이터로 보존. 펫·탈것·치장 슬롯도 미래 확장 대상.
- 방향키/WASD 실시간 이동, 같은 방만 동기화. 서버가 위치·이동 제한·경계·과도한 겹침 방지와 권한을 판정.
- 채팅: 같은 교실, 닉네임 표시. 전체 ON/OFF, 개별 금지, 기록 확인, 전체 삭제. 필터 처리 별도 모듈.
- 기본 맵은 빈 우주에 부서행성/별 쉼터 배치. 청소·일기·독서·교과행성, 별상점, 모두를 모으는 밝은 큰 별 광장, 자기 정보, 알림장 역할의 속보별. 구체적 상점/제작 등의 운영 기능은 이후 확장.
- 부서행성은 아지트/미니홈피 개념. 한 아바타는 한 부서만 가입, 자유 가입/탈퇴, 가입자만 출입. 향후 레벨별 접근 맵 5~10개. 경고 누적 후 검은별 부착과 패널티 계획이며 경고 횟수/패널티 세부값 미정, 임의 확정 금지.
- 근처 오브젝트에 E키 안내 및 상호작용 버튼, 모바일 터치 버튼. 굴러다니는별 미션 안내, 보물별 아이템 획득 등 기본 반응.
- 인벤토리 항목 최소 id/name/description/icon/quantity/type. 별 파편은 정수 재화, 지출 단위는 자연수(잔액 0 허용 여부 등은 구현 계약에 명시). 구매·기능·경험치·조합 재료로 향후 연결.
- 아이템 LV1~5, 아바타 레벨보다 높은 아이템 사용 불가. 타인 대상 사용 가능하나 낮은 레벨이 높은 레벨 대상에게 사용 불가. 모두 사용 가능한 충돌 시 높은 레벨 우선, 동레벨/동시성 세부 규칙 미정. 실제 상점/조합/경험치 구매를 첫 단계에 모두 구현하지 않음.
- 교사 관리: 접속 학생, 강제 퇴장, 이동 잠금, 개별 채팅 금지, 전체 채팅 ON/OFF, 지정 위치/선생님 앞으로 모으기, 개별·전체 아이템 지급, 별 파편 지급. 교사 권한은 서버 인증으로 검증하며 화면 버튼 여부를 믿지 않음.
- 서버가 방·학생·위치·채팅·아이템·교사 권한·오브젝트 상태 관리. 학생의 임의 아이템/역할 변경 요청 거절. 교사 생성 인증 및 허용 닉네임 검증 필요.
- 미래 확장: 퀘스트, 미션, 상점, 경험치/레벨/화폐, 팀, 보물찾기, OX 퀴즈, 자리 배치, 출석, 교사 미션 배포, 꾸미기, 맵, 펫/NPC, 1:1 미니게임(원문 '핵맨', 오목, 숫자 기억력, 숫자 야구). 초기에는 연결 가능한 구조만.
- 간단한 구조·기능별 파일·주석·초보자 README·설치 명령·실행 순서·필요시 .env.example. 개인정보 최소화. 익명으로 다음 수업에도 성장 기록을 복구할 식별 수단은 영속 저장 추가 시 설계해야 함(닉네임 단독을 인증으로 사용하지 않음).
- STEP 1 기술 구조 제안 → STEP 2 폴더 구조 → STEP 3 학생 접속/방 입장/캐릭터 생성/이동 → STEP 4 사용자 테스트 안내. 사용자의 정상 작동 확인 후 STEP 5 채팅 → STEP 6 상호작용 → STEP 7 아이템 → STEP 8 교사 관리. 각 단계 실행 검증 후 다음으로 진행. 오류 원인 수정 원칙.

## 서버 비교 결과

- 권고: 첫 테스트는 직접 구현한 Node.js+Socket.IO 서버를 로컬에서 검증한 뒤 Render Free에 배포 가능한 구조. 이동 등 순간 상태는 서버 메모리, 추후 성장/재화/부서 등의 지속 상태는 저장 계층을 통해 외부 DB로 분리. 서버 작성/보안/운영은 직접 구현해야 한다.
- Render는 WebSocket 지원, Free 인스턴스 시간 월 750시간/워크스페이스. 비활성 15분 후 정지, 다음 요청 시 약 1분 재가동. 재시작/재배포/정지 시 로컬 파일과 메모리 상태를 보존할 수 없음. Free Postgres는 30일 만료이므로 장기 저장 기본안으로 쓰지 않음. 대역폭/빌드 별도 한도, 결제수단이 없으면 해당 한도 초과 시 서비스/빌드 중단 조건. 30명 실제 성능은 테스트 전 보장하지 않음.
- Firebase Spark Realtime Database: 동시 연결 100, 저장 1GB, 다운로드 월 10GB. 연결은 사용자 숫자와 다르며 탭/서버 연결도 포함. 웹 지원 및 저장에 적합. 초당 이동을 전부 DB에 쓰는 설계는 트래픽이 커지고 서버 판정 구현이 별도 필요하므로 초기 게임 서버의 1순위로 권고하지 않음. Cloud Functions는 Spark 미제공, Blaze 사용 전제. Firebase 저장 계층 추가는 향후 선택지.
- 뒤끝: 공식 문서는 Unity/C# SDK 중심. 순수 브라우저 JavaScript 매치 지원은 확인되지 않아 불가능하다고 단정하지 않되 첫 권고에서 제외. FREE 기능별 호출 한도 존재: 예를 들어 게임 정보 관리 월 5만, 상태 조회 월 10만. '모든 기능 10만 무료'로 해석하면 안 됨. DB/푸시/클라우드 세이브는 FREE에서도 초과 과금 조건이 명시되어 있음.
